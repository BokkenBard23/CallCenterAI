# Domain Concepts

## SmartLogger Matching Engine

SmartLogger is the core **morphological matching engine** that powers keyword detection in call transcripts. It uses pymorphy3 for Russian language morphology, handling inflection, aspectual pairs, and dictionary-based phrase matching.

### How It Works

1. **Dictionary Loading** — Keywords are loaded from XML dictionaries or the database, each with morphological attributes (part of speech, case, tense constraints)
2. **Tokenization** — Transcript text is split into tokens using `tokenizer.py`
3. **Lemma Matching** — Each token is lemmatized and matched against dictionary entries using pymorphy3
4. **Phrase Assembly** — Individual matches are assembled into multi-word phrases with `word_distance` tracking
5. **DisplayToken Generation** — Matches are converted to DisplayToken objects for frontend rendering

### Key Matching Rules

- **Aspectual pairs**: Perfective/imperfective verb forms are treated as equivalent
- **Morphological flexibility**: Noun cases, adjective agreements, and number variations are normalized
- **Distance tolerance**: Multi-word phrases allow configurable `word_distance` between components
- **Channel attribution**: Matches are attributed to OPERATOR, CLIENT, or ANY speaker channels

## DisplayToken Model

The DisplayToken is the canonical data structure representing a matched phrase:

| Field | Type | Description |
|-------|------|-------------|
| `text` | string | The matched text span |
| `type` | WORD \| PHRASE \| LEXEME \| BRACKET | Match granularity |
| `channel` | OPERATOR \| CLIENT \| ANY | Speaker attribution |
| `word_distance` | number | Distance between phrase components |
| `is_error` | boolean | Whether this is an error/flagged match |
| `is_exact` | boolean | Whether this is an exact (non-morphological) match |

### Depth Levels (Highlight Colors)

DisplayTokens carry a depth level that determines visual highlight intensity:

| Depth | Severity | Color |
|-------|----------|-------|
| 1 | Critical | Red |
| 2 | Important | Orange |
| 3 | Moderate | Amber |
| 4 | Info | Teal |
| 5 | Reference | Blue |
| 6 | Legacy | Brown |

## Quality Scoring

The quality scoring rubric evaluates agent performance across multiple dimensions:

- **Greeting protocol** — Proper opening and closing
- **Active listening** — Acknowledgment of customer statements
- **Conflict management** — Handling of difficult interactions
- **Product knowledge** — Accuracy of information provided
- **Compliance** — Adherence to mandatory scripts

Scores are generated by the LLM analysis pipeline and displayed in the `QualityScorePanel` component.

## Sentiment and Conflict Detection

LLM-powered analysis provides:

- **Sentiment scoring** — Overall call sentiment (positive/neutral/negative)
- **Conflict detection** — Identification of escalating situations
- **Profanity filtering** — Language violation detection
- **Topic classification** — Automatic call topic categorization

These analyses run in parallel with rule-based matching. The LLM results are non-blocking — the frontend displays keyword matches first, then augments with AI insights when available.

## Dictionary Management

Keyword dictionaries are hierarchical XML structures managed through the Dictionary Editor:

### Dictionary Structure

- **Root categories** → **Subcategories** → **Conditions** (individual keyword entries)
- Each condition has: text, morphological attributes, depth level, channel filter
- XML export preserves full SmartLogger round-trip compatibility

### Mining Operations

Mining identifies dictionary improvement opportunities:

- **False negatives** — Dialogues where expected matches failed
- **Similar dialogues** — Pattern-based similarity detection
- **Audit** — Systematic review of matching quality
- **Phrase suggestions** — AI-generated new keyword candidates

### Validation Rules

The `validator.py` module enforces dictionary consistency:
- No duplicate keywords within the same category
- Morphological attributes must be valid for the given word
- XML structure must conform to SmartLogger schema

## PII Masking Rules

Personal data protection uses Presidio with 7 custom Russian-language recognizers (Russian Federal Law 152-ФЗ compliance). PII masking runs **BEFORE** session storage — unmasked data never persists.

### Prerequisites

- spaCy (`ru_core_news_sm` model) required for Presidio Russian NER
- See [`docs/ops/pii-masking-setup.md`](/docs/ops/pii-masking-setup.md) for full setup guide
- If enabled but unavailable, upload returns HTTP 503 (hard compliance guard)

### Recognizers

| Recognizer | Pattern |
|------------|---------|
| Passport number | Russian passport format (XX XXXXXX) |
| Phone number | Russian formats (+7, 8, mobile) |
| INN/TIN | 10 or 12 digit tax identification |
| SNILS | Insurance number (XXX-XXX-XXXX XX) |
| Bank card | 16-digit card numbers |
| Address | Russian address patterns |
| Name | Russian full name patterns |

## Time-Gap Filtering (ExtraLimitations)

SmartLogger XML dictionaries support **temporal/positional windows** via `<ExtraLimitations>`, controlling **where** in a dialogue keyword matches are kept or discarded. This is NOT a silence/pause filter despite the `Gaps` naming.

### SearchSpecifier — Filter Mode

| SearchSpecifier | Effect |
|-----------------|--------|
| `OnlyInGaps` | **INCLUDE** — keep only matches inside the window |
| `ExcludeGaps` | **EXCLUDE** — drop matches inside the window |

### EventType

| Type | Behavior |
|------|----------|
| `StartEnd` | Window anchored at dialogue start (`First`) or end (`Last`), sized by `Seconds`, `Words`, or `Phrases` |
| `Parent` | Window anchored on parent node match times, with `Before`/`After` direction and `First`/`Last`/`Each` selector |

Multiple `<Limit>` and `<ExtraLimitation>` entries combine via **AND** — all conditions must be satisfied.

### Timestamp Source

RTF timestamps (`H:MM:SS`) are extracted by `smartlogger.rtf_parser.extract_dialogue()` and converted to float seconds via `rtf_parser._parse_timestamp_to_seconds()`. If timestamps are absent, filtering is a no-op.
